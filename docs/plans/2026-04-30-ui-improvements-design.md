# Пакет UX-улучшений · 6 фич

Дата: 2026-04-30
Статус: утверждено пользователем

## Цели

Закрыть видимые UX-пробелы после первого боевого использования приложения:
быстрая навигация, источник дедлайнов из входящего письма, заметность
просрочек, аналитика по объекту, доступ ко всем файлам дела и сохранение
истории файлов при перезаливке.

## 1. Иконки в боковом меню

- Библиотека: `lucide-react` (~3 кб на иконку, tree-shake, line-style).
- Маппинг:

| Пункт меню | Иконка lucide |
|---|---|
| Сегодня | `LayoutDashboard` |
| Дела | `Folder` |
| Входящие | `Inbox` |
| Реестр исх. | `Send` |
| Календарь | `Calendar` |
| Аналитика | `BarChart3` |
| МКД | `Building2` |
| Контрагенты | `Users` |
| Договоры | `FileText` |
| Пользователи | `UserCog` |
| Шаблоны | `FilePlus` |

- Размер 16 px, тон `var(--ink-2)`.
- Заменяет существующий точечный маркер `•` слева от лейбла.
- Активный пункт — иконка `var(--bordeaux)`.

## 2. Поле «Срок устранения по письму» во входящем

- БД: добавить колонку `IncomingLetter.requestedRemedyDate DateTime?`.
- Миграция: `prisma db push` (используется в проекте, не migrate dev).
- UI:
  - В форме создания/редактирования входящего (`InboxScreen` /
    `AddIncomingModal`) — date input «Срок устранения по письму».
  - В карточке входящего — отображение даты, если есть.
- Использование:
  - При создании дела из письма (`/cases/new?from=<incoming>`) —
    автоподстановка `deadlines.remedy = incoming.requestedRemedyDate`.
  - При генерации T3/T6 — поле `remedyDate` подставляется из этого
    значения (если не переопределено пользователем в форме).

## 3. Подсветка просроченной задачи в реестре дел

- В `CaseRowsTable.Row` — `<tr style={{ background }}>` где background
  становится `var(--bordeaux-bg)` если `nearestDeadline.days < 0`.
- При hover — чуть темнее (`color-mix(in srgb, var(--bordeaux-bg) 80%, var(--ink) 8%)`).
- Никакой анимации, никакого жёсткого красного — придерживаемся палитры.

## 4. Drill-down по объектам МКД

- `/buildings` — превращается из плоского списка в справочник с
  колонками: Адрес · СПО · Дел всего · Открытых · Горящих.
- Строка кликабельна → `/buildings/[id]`.
- `/buildings/[id]` — новая страница:
  - Шапка: полный адрес, СПО, договор, кнопка «＋ Дело по объекту».
  - Блок «Активные дела» — `CaseRowsTable` с фильтром `state != closed`.
  - Блок «Закрытые дела» — свёрнутая таблица.
  - Блок «Хронология объекта» — события всех дел этого объекта,
    отсортированные по дате (визиты, отправленные письма, состояния).
  - Блок «Входящие по объекту» — все `IncomingLetter` с этим
    `buildingId`, со ссылками на дела или метку «без дела».

Никакой новой сущности — только агрегация по `buildingId`.

## 5. Все файлы дела + ZIP-выгрузка

- Универсальный эндпоинт `/api/files/download?path=<rel>` с:
  - проверкой `auth()` (только для залогиненных);
  - whitelist префиксов: `incoming/`, `outbox/`, `visits/`, `signatures/`, `edo/`;
  - блокировкой `..` и абсолютных путей.
- На карточке дела — новый блок «Все файлы дела» с группировкой:
  - Входящие письма (PDF + вложения)
  - Сгенерированные документы (.docx)
  - Подписи УКЭП (.sig)
  - ЭДО-пакеты (.zip)
  - Фото с выездов
- Кнопка «↓ Скачать всё ZIP-ом» → новый эндпоинт
  `/api/cases/[id]/files.zip` собирает все файлы дела в архив на лету
  через jszip (он уже в зависимостях).
- Структура ZIP:
  ```
  <caseNumber>/
    incoming/<incoming.number>.pdf
    documents/<outgoingNumber>_<title>.docx
    signatures/<docId>.sig
    edo/<docId>_package.zip
    visits/<visitDate>_<idx>.jpg
  ```

## 6. Версионирование файлов

- Новая таблица `FileRevision`:
  ```prisma
  model FileRevision {
    id           String   @id @default(cuid())
    ownerType    String   // "incoming" | "document" | "visit_photo"
    ownerId      String   // FK по ownerType
    version      Int      // автоинкремент в рамках owner
    path         String
    filename     String
    size         Int
    mime         String?
    uploadedById String?
    uploadedAt   DateTime @default(now())
    comment      String?

    @@unique([ownerType, ownerId, version])
    @@index([ownerType, ownerId])
  }
  ```
- Применяется ко всем трём типам: входящие письма, сгенерированные
  документы, фото визитов.
- Поведение при перезаливке:
  - Старая запись `version=N` остаётся в БД и в storage.
  - Создаётся новая запись `version=N+1` с новым файлом.
  - Поле owner-объекта (`attachedFile`/`renderedDocxPath`/`photos`)
    обновляется на путь к последней версии — для обратной совместимости.
- UI:
  - Рядом с файлом — пилюля `v3 · история` (link).
  - Клик открывает модалку со списком версий: дата, размер, кто загрузил,
    комментарий, кнопки «↓ скачать» и «↩ откатить как новую версию N+1».

## Порядок реализации

Каждый пункт = отдельный коммит, чтобы можно было откатить точечно
если что-то пойдёт не так.

1. **Иконки + красная подсветка просрочки** — мгновенно видно, нет
   миграций, низкий риск.
2. **Поле «Срок устранения по письму»** — миграция + UI формы +
   подстановка в дело.
3. **Все файлы дела + ZIP** — универсальный download endpoint, новый
   блок на карточке дела, ZIP endpoint.
4. **Версионирование** — миграция схемы, обёртка вокруг сохранения
   файлов, UI истории версий.
5. **Drill-down `/buildings/[id]`** — новая страница, доработка списка
   `/buildings`.

## Что НЕ делаем сейчас (YAGNI)

- Поиск по содержимому файлов (OCR PDF) — отдельная задача.
- Diff между версиями docx — нерационально без серьёзной работы.
- Drag-and-drop загрузка файлов — оставляем нативный `<input type="file">`.
- Редактор шаблонов с превью — текущий конструктор блоков остаётся.
